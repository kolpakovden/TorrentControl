# TorrentControl

Монитор µTorrent для Windows с автозагрузкой новых публикаций фильмов. Версия **1.9**.
Автозагрузка включается отдельно. Очистка раздач работает только в режиме **DRY RUN**:
отчёт о кандидатах строится, но файлы и раздачи не удаляются и не останавливаются.

## Обновление до 1.9

1. Скопировать исходные файлы версии 1.9 (включая новый `Cleanup.ps1`) в прежнюю папку `C:\TorrentMonitor`
   с заменой (папка `scripts` нужна только GitHub Actions, на ПК её можно не копировать).
2. Сохранить локальные `config.json`, `credential.xml`, `state.json`, `feed-state.json`, `autoload.json`,
   `auto-state.json` и резервные копии `*.json.bak`. `state.json` версии 1.8 читается как есть: срок наблюдения
   сохраняется, а учёт отдачи по часам начинается с первого опроса 1.9.
3. Запустить **2-Run-once.cmd** или дождаться задания `TorrentMonitor-DF`.
4. Смотреть `report.html`, `cleanup.html` (очистка, DRY RUN), `films.html` и `auto-downloads.html`.
   Первые кандидаты на очистку возможны примерно через 73 часа непрерывной работы монитора после обновления.

При обновлении с 1.7 или 1.8 повторно запускать `1-Setup.cmd` и `6-Enable-autoload.cmd` не требуется.
При обновлении с 1.6 дополнительно запустить **6-Enable-autoload.cmd** (µTorrent должен быть запущен).
Если монитор уже выполняется, включение может сообщить об ошибке блокировки: повторить после завершения опроса.
**7-Disable-autoload.cmd** выключает только будущие добавления; текущие торренты продолжают работу.

## Автозагрузка

При первом включении текущая лента и ранее замеченные ID тем становятся исходным списком.
**Они не скачиваются задним числом.** Отбираются только темы, впервые замеченные после включения.
Изменение хеша в прежней теме не запускает загрузку другой версии. Повторное включение сохраняет исходный список и журнал.

- Раздел RuTracker **252**. Качество по названию: WEB-DL, WEB-DLRip, BDRip.
- Озвучка по названию: Dub, MVO, DVO либо явное упоминание дубляжа/многоголосого перевода.
  Русские субтитры без такой озвучки не подходят. CAM/CAMRip/HDCAM/HDTS/TS/TC исключены.
- Это фильтр названия, а не анализ аудиодорожек. Разные релизы одного фильма имеют разные хеши и могут попасть в очередь.
- Назначение: **`D:\Фильмы\rt-<номер темы>`**. Отдельная папка исключает смешивание файлов разных релизов.
- Размер одной раздачи не ограничен. На D: сохраняется **20 ГиБ** запаса;
  из свободного места дополнительно вычитается объём ещё не скачанных данных всех заданий на D:.
- Задание считается завершённым, только если PROGRESS = 1000 **и** REMAINING = 0. Счётчик DOWNLOADED
  на это не влияет: у раздач, добавленных с готовыми данными, он равен 0, у долгих раздач больше размера.
  Для незавершённого задания на D: резервируется наибольшая из оценок — REMAINING, SIZE − DOWNLOADED
  и доля по PROGRESS (с округлением вверх), поэтому одно неверное значение не скрывает недокачанные данные.
  Оценка консервативна, особенно при предварительном выделении файлов. Задания на F:, E: и других дисках
  резерв D: не расходуют. Расчёт идёт в точной десятичной арифметике по списку WebUI, повторно
  запрошенному непосредственно перед запуском µTorrent.
- Добавления приостанавливаются, если безопасный бюджет нельзя подтвердить: путь незавершённого задания
  неизвестен или не вида `X:\…` (`UnknownIncompletePath`); у задания на D: размеры отсутствуют, текстовые,
  дробные, отрицательные, больше 1 ПиБ или PROGRESS > 1000 (`UnknownRemainingSize`); свободное место
  не определено (`FreeSpaceUnknown`); резерв меньше 20 ГиБ (`InvalidAutoSettings`).
  Другие приложения и ручные загрузки тоже могут расходовать диск.
- Не более **одного добавления за опрос**; проверяются до трёх ожидающих записей с чередованием очереди.
- Хеши, уже имеющиеся в µTorrent на любом диске, пропускаются.
- Перед запуском проверяются SHA-1 infohash, точный размер, имена и пути внутри метаданных.
  Отклоняются выходы из папки, ссылки, зарезервированные Windows-имена, конфликтующие пути и исполняемые файлы.
  Внешние поля `.torrent`, не защищённые infohash, заменяются известным публичным трекером.
- Ответ WebUI проверяется строго до любого действия автозагрузки — и первый список опроса, и повторный
  запрос непосредственно перед запуском µTorrent: типы и диапазоны полей 0, 1, 3, 4, 5, 6, 8, 12, 18 и
  отсутствие повторяющихся хешей. Хотя бы одно некорректное значение останавливает автозагрузку в этом опросе
  (`ClientDataInvalid:<поле>` в `monitor.log`); подтверждения и отправки не выполняются.
- Перед отправкой хеш ищется и в списке WebUI, и в `resume.dat`. Пустой список или список, потерявший раздачи
  за время проверки, не считается доказательством отсутствия: отправка откладывается до следующего опроса.
- До вызова µTorrent сохраняется запись `Submitted`. При сбое или перезапуске она не отправляется повторно.
- На следующем опросе проверяется фактический путь. Пока он не подтверждён, следующие добавления ждут.
  Если хеш оказался в другой папке, раздача **не останавливается и не изменяется**: это может быть ручное
  или ранее существовавшее задание, принадлежность которого доказать нельзя. Запись получает «Нужна проверка»,
  следующие добавления блокируются.
- Если переданный хеш не появился в клиенте за 2 часа или его путь не подтвердился за 24 часа,
  запись тоже получает «Нужна проверка». Повторной отправки не бывает.
- После проверки в µTorrent **8-Review-autoload.cmd** (с вводом `YES`) помечает такие записи
  «Проверено пользователем» и снимает блокировку. Записи остаются в журнале; их хеши больше не отправляются.
- `auto-state.json` записывается атомарно, предыдущая версия хранится в `auto-state.json.bak`.
  Если журнал пропал, а копия осталась, автозагрузка и повторное включение останавливаются (`AutoStateBackupPresent`).
- Уже подтверждённая раздача не добавляется заново, даже если пользователь затем удалил её из клиента.

Скрипт использует проверенный на µTorrent 2.2.1 build 25534 параметр `/DIRECTORY`.
Клиент должен работать на том же компьютере, что и монитор, в единственном экземпляре.
Общие папки WebTLO и настройки клиента не изменяются. Автозагрузка предполагает сохранение
настроек, проверенных пользователем: новые задания запускаются, а перенос завершённых файлов
применяется только к папке загрузки по умолчанию на E:.

## Лента и метаданные на GitHub

RuTracker недоступен с компьютера с раздачами, поэтому публичную Atom-ленту раздела 252 получает GitHub Actions,
а клиент читает копию `data/forum-252.json` через `raw.githubusercontent.com`. Старый `feed-proxy.txt` не используется.

**Почему обновление бывает редким.** GitHub не гарантирует запуск по расписанию. С 24.10 по 12.11.2026
из 48 запланированных запусков в сутки фактически создавалось около 4 (интервалы: медиана 5,5 ч, максимум 11 ч),
и все созданные запуски завершились успешно. Задержки возникают в планировщике GitHub (событие `schedule`
откладывается или пропускается при нагрузке), а не в скрипте или источнике. Так же вёл себя Cache film metadata.

**Как устроено обновление (1.8).**
- `scripts/refresh_feed.py` публикует снимок только после строгих проверок: адрес и `id` раздела, отсутствие DTD,
  каждая запись (`/t/<номер>`, заголовок, дата) и собственное время ленты `<updated>` — не старше 2 часов и не
  в будущем относительно момента получения (наблюдаемая задержка не больше 10 минут). Старый документ
  не публикуется как свежий; время снимка и номер `sequence` только растут, конкурирующие запуски не затирают
  более новый снимок.
- **Refresh film feed** запланирован на 4 слота в час (7, 22, 37, 52 мин, вдали от начала часа).
  **Cache film metadata** служит вторым, независимым триггером: если снимку больше 40 минут, он сначала обновляет
  ленту. Это увеличивает число попыток, но гарантировать запуск GitHub Actions не может.
- Неизменная лента переопубликуется не чаще раза в 25 минут. При ошибке прежний снимок не трогается, а код
  (`UpstreamHTTP=503`, `UpstreamStale`, `UpstreamInvalid:…`) записывается в `data/feed-status.json` вместе
  с временем попытки и числом ошибок подряд; после успеха статус очищается.
- Снимок содержит диагностику: `sequence`, `trigger`, `source_updated`, `previous_fetched_at`, `gap_hours`, `coverage`.

**Почему темы не теряются при перерывах.** Лента содержит 50 последних обновлённых тем; сейчас это 13–19 дней.
Пока перерыв в обновлении (GitHub или выключенный ПК) короче этого окна, следующий снимок содержит все
пропущенные темы, а журнал автозагрузки (номера тем и хеши) не даёт добавить уже обработанное повторно.
Если окно всё же превышено, снимок помечается `possible_gap`, клиент пишет `FEED GAP` в `monitor.log`
и предупреждение в `films.html`: такие темы этим источником не восстановить. Поэтому отдельная история
и резервный источник не добавлены — при текущем темпе (~3 темы в сутки) они не нужны.

**Клиент.**
- Как и раньше, отклоняется копия старше 6 часов, из будущего, с чужим источником или несовпадающим числом записей.
- Новое: копия старше уже использованной (кэш CDN, откат коммита) — `MirrorRollback`; свежая `fetched_at`
  при старом документе Atom — `MirrorSourceStale`.
- Пока лента устарела, новые темы не добавляются, но очередь автозагрузки (подтверждение пути, метаданные,
  ожидание места) продолжает обрабатываться.
- `report.html` и `films.html` показывают время и возраст копии, номер снимка и источник запуска, а при ошибке —
  причину: GitHub не запускал обновление или источник вернул ошибку (по `feed-status.json`).

Workflow **Cache film metadata** запускается после успешного обновления ленты и по своему расписанию
(23-я и 53-я минуты), обрабатывая до трёх подходящих хешей за запуск.
`aria2 --bt-metadata-only=true --bt-save-metadata=true` получает только метаданные, без содержимого фильмов.
Успешные результаты сохраняются в `data/metadata/<hash>.json`. Недоступные пиры повторно проверяются не чаще раза в час.
Клиент ждёт появления метаданных; отсутствие файла в кэше не запускает загрузку вслепую.
Метаданные кэшируются и по устаревшей (до 14 дней), но подлинной копии ленты: сбой ленты больше не останавливает кэш.
Обе задачи доступны для ручного запуска через Actions (**Run workflow**).

GitHub получает только публичную ленту/метаданные. Пароли, ключи RuTracker, пути и статистика локального клиента туда не отправляются.
На компьютере с раздачами не требуется aria2 или Python. При сетевой ошибке наблюдение за текущими раздачами продолжается.

Atom содержит `updated`, а не `published`: впервые замеченная тема не обязательно только что создана.

## Мониторинг хранения

- Отслеживаются все папки на **D: и F:**.
- **Весь E:** — постоянный архив. **C:** — системный. Оба диска исключены из отбора на очистку.
- Решение по каждой раздаче — «Оставить», «Недостаточно данных» или «Кандидат на очистку» — принимается
  по правилам очистки 1.9 (см. ниже) и одинаково показывается в `report.html` и `cleanup.html`.
- «Признак спроса» (справочно) — только то, что наблюдает наш клиент: прирост отдачи с прошлой проверки, текущая скорость отдачи
  (поле 8 списка WebUI) или подключённые к нам пиры, не сиды (поле 12). Пиры и сиды «в рое» (поля 13 и 15) —
  сведения о рое в целом; они показаны справочно и на решение не влияют: их наличие не доказывает спрос на нашу раздачу.
- Перерыв больше часа, остановка, ошибка и неполная загрузка сбрасывают справочный период тишины.
  Смена пути или сброс счётчиков начинают наблюдение заново.
- Данные клиента не доказывают полного отсутствия спроса. Автоматическое удаление **не реализовано**.
- Временные сбои не стирают историю. Пустой список WebUI при непустой истории останавливает опрос целиком
  (`EmptyTorrentList`); раздачи с временно неизвестным путём или некорректными полями сохраняют прежнюю запись.
- Удалённая из клиента раздача сразу пропадает из отчёта, а её история удаляется после трёх подряд проверок
  без неё и не ранее чем через 6 часов. Отсутствие засчитывается, только если все строки списка корректны
  и раздачи нет и в `resume.dat`; повреждённый ответ никогда не приближает удаление истории.
  Возвращение раньше сохраняет срок хранения, но сбрасывает период тишины.
- Некорректные значения в отчёте показываются как «н/д», а не как 0, и не прерывают опрос.
- `state.json` записывается атомарно, предыдущая версия — `state.json.bak`. Повреждённый файл (`StateUnreadable`)
  или пропавший файл при оставшейся копии (`StateMissingBackupPresent`) останавливают опрос без перезаписи.
  Чтобы намеренно начать историю заново (или если в клиенте действительно не осталось раздач),
  удалите `state.json` вместе с `state.json.bak`.

Если старый WebUI не сообщает путь, `resume.dat` читается локально без изменения файла.
Можно указать путь через `resume-path.txt`. Неизвестные и неоднозначные пути исключаются из отбора.

## Очистка раздач по фактической отдаче (1.9, только DRY RUN)

**DRY RUN — файлы и раздачи не удаляются.** В версии 1.9 нет ни одной операции удаления, остановки раздач
или изменения настроек µTorrent; статический тест проверяет это для всех файлов программы.

### Правила отбора
Раздача — **кандидат на очистку**, только если одновременно:
- полностью скачана: PROGRESS = 1000 **и** REMAINING = 0;
- путь на **D:** или **F:** (C:, E: и прочие диски не очищаются никогда);
- наблюдается системой не менее **30 дней**;
- в **каждые** из трёх последних последовательных суток отдала **менее 1 ГиБ** (порог к каждым суткам отдельно,
  а не к сумме за 72 часа; ровно 1 ГиБ — уже не «менее»; сутки с 1,2 ГиБ не дают стать кандидатом,
  пока не пройдут три новых «тихих» суток);
- в момент проверки нет отдачи (поле 8) и подключённых скачивающих пиров (поле 12);
- раздача запущена (не остановлена, не на паузе, не в очереди, не проверяется, без ошибки), ответ WebUI
  и история наблюдений корректны.

Сиды на решение не влияют: «Сидов_в_рое» показывается справочно, а если в рое не больше одного сида
(других сидеров может не быть), ставится предупреждение «Редкая раздача».

### Как хранится и считается отдача
- Источник — накопительный счётчик **UPLOADED** (поле 6) WebUI µTorrent 2.2.1. Разница между двумя соседними
  опросами точна и не зависит от того, сколько опросов было пропущено, пока счётчик не прерывался.
- Для каждой раздачи в `state.json` хранятся: `uploadSince` — начало текущей непрерывной истории,
  `uploadHours` — компактная строка `час,внутри,через_границу;…` по часам UTC (только ненулевые часы за последние
  ~75 часов) и `uploadNote` — причина последнего перезапуска истории. «Внутри» — отдача между опросами в пределах
  одного часа; «через границу» — интервал опроса, пересёкший начало следующего часа (≤ 60 минут).
- История непрерывна, только пока каждый опрос видит раздачу завершённой, запущенной, с известными пирами,
  по тому же пути, счётчик не уменьшается и между опросами не больше **60 минут**. Иначе — пропуск опросов
  более часа, сброс счётчика, смена пути или хеша, исчезновение из списка, остановка, перевод часов назад,
  повреждённая история — история **начинается заново** с текущего опроса. Неизвестный промежуток никогда
  не считается нулевой отдачей: такая раздача остаётся «Недостаточно данных», пока не накопит 73 часа.
- Пропуск одного-трёх опросов подряд (до 60 минут) данных не теряет: отдача за этот промежуток точно известна
  по счётчику и учитывается консервативно (см. ниже). Порог 60 минут — константа `MaxGap`.
- Отрицательной отдачи не бывает (уменьшение счётчика = перезапуск истории); значения больше 1 ПиБ за интервал
  считаются недостоверными; суммы — целые 64-битные числа без переполнения и округлений.
- Повторный запуск монитора ничего не считает дважды: каждый опрос сравнивается только с последним сохранённым.
  История сохраняется **до** записи отчётов; если сохранить её не удалось, отчёты не обновляются, а следующий
  опрос считает тот же интервал один раз.
- Размер: при 450 раздачах `state.json` занимает около 0,25 МБ; даже 600 раздач с отдачей каждый час — меньше 2 МБ
  (это проверяется тестом, в том числе в Windows PowerShell 5.1).

### Почему это три полных 24-часовых окна при опросе раз в 15 минут
Пусть H — текущий час UTC. «Сутки 1» — целые часы H−24…H (до момента проверки), «сутки 2» — H−48…H−24,
«сутки 3» — H−72…H−48. Каждое окно — 25 часов и **содержит** соответствующие точные сутки: последние 24 часа
до проверки, 24 часа до них и ещё 24 часа до них. В сумму окна входят все интервалы опросов внутри его часов
и **целиком** все интервалы, хотя бы частично его задевающие (граничный час общий для соседних окон).
Поэтому значение окна — верхняя оценка отдачи за соответствующие сутки: если оценка меньше 1 ГиБ,
то и реальная отдача за эти сутки меньше 1 ГиБ. Обратная ошибка возможна только в безопасную сторону
(раздача с реальными 0,97 ГиБ может остаться «Оставить»). Для всех трёх окон нужна непрерывная история
с начала часа H−72, то есть около 73 часов.

### Режимы и отчёт
- `cleanup.json` (необязательный): `{"mode": "DryRun"}` (по умолчанию, если файла нет) или `{"mode": "Disabled"}`.
  `Enabled` в 1.9 **не поддерживается и не включается**: при таком значении работает только Dry Run, а в отчёте
  выводится предупреждение. История отдачи накапливается в любом режиме.
- `cleanup.html` и `cleanup.csv`: решение и причина, название, путь, размер, хеш, возраст наблюдения, отдача
  за каждые из трёх суток и за 72 часа (верхние оценки, «н/д» — нет полной истории), текущая скорость отдачи,
  подключённые пиры, сиды (справочно), «Редкая раздача», принадлежность (TorrentControl — подтверждённая
  автозагрузкой в `D:\Фильмы\rt-<тема>`; иначе «Ручная»). Сверху — сумма потенциально освобождаемого объёма.
  В каждом отчёте и в каждой строке CSV указано: «DRY RUN — файлы и раздачи не удаляются».
- `monitor.log`: `CLEANUP DRY RUN: candidates=…, GiB=…, insufficient=…, keep=…`.

### Ограничения будущего удаления (не реализовано, обязательны для следующей версии)
- C: и E: защищены полностью; удаление возможно только на D: и F:.
- Удалять файлы автоматически можно только у раздач с **доказанной принадлежностью TorrentControl**
  (запись автозагрузки «Добавлено, путь подтверждён», совпадающий хеш, путь внутри собственной папки
  `D:\Фильмы\rt-<тема>`) и проверенным составом файлов по сохранённым метаданным.
- Ручные раздачи D:/F: (включая хранительские) показываются кандидатами, но автоматически не удаляются.
- Символические ссылки, junction и другие точки повторной обработки на всём пути, файлы, общие с другими
  раздачами, и неизвестные или неоднозначные пути блокируют удаление.
- Непосредственно перед удалением все условия повторно проверяются по свежему ответу WebUI и `resume.dat`;
  любое расхождение — отказ. Обход этих ограничений ради освобождения места не допускается.

### План перехода к реальному удалению (следующая версия)
1. Минимум неделя работы 1.9 в Dry Run и ручная сверка `cleanup.csv` с µTorrent.
2. Отдельный PR: режим `Enabled` только через явное подтверждение пользователя, по одной раздаче за опрос,
   только раздачи TorrentControl; журнал действий записывается до действия.
3. Перед каждым удалением — свежий WebUI, повтор всех правил, проверка путей и ссылок, сверка файлов с метаданными.
4. Сначала — только снятие раздачи из клиента без удаления файлов, затем отдельным шагом — удаление файлов.
5. Отдельные тесты на каждый отказ и ручная проверка на тестовых данных до включения на рабочем ПК.

## Установка с нуля

Нужен Windows PowerShell 5.1. Скопировать пакет на компьютер с µTorrent, запустить `1-Setup.cmd`,
указать WebUI (обычно `http://127.0.0.1:9090`) и учётные данные. Пароль хранится в `credential.xml` через Windows DPAPI.
Задание `TorrentMonitor-DF` выполняется каждые 15 минут, пока пользователь вошёл в Windows.
Блокировка экрана и отключение RDP допустимы; выход из учётной записи прекращает запуски.
Автозагрузку при необходимости включить отдельно через `6-Enable-autoload.cmd`.

## Диагностика и проверка

- `monitor.log` — ошибки и результаты наблюдения; `auto-downloads.html` — состояния очереди.
- «Ожидает метаданные» — GitHub ещё не получил `.torrent`, проверка повторится.
- «Ожидает место» — не хватает места с учётом запаса и незавершённых заданий.
- «Передано клиенту» — ждём появления хеша и пути в WebUI/resume.dat. Повторной передачи не будет.
- «Нужна проверка» — проверьте задание и путь в µTorrent; следующие добавления блокируются.
  Затем запустите `8-Review-autoload.cmd`. Не удаляйте `auto-state.json` для обхода блокировки:
  это журнал защиты от повторной отправки.
- Ошибки в `monitor.log` содержат код: `EmptyTorrentList`, `UnsupportedRowFormat`, `StateUnreadable`,
  `StateMissingBackupPresent`, `TokenMissing`, `TorrentListMissing`; во всех этих случаях история не изменяется.
- Ошибка `UnknownIncompletePath` — дождаться сохранения resume.dat и повторить опрос.
- «Подборка фильмов не обновлена: … MirrorStaleOver6Hours» — копия ленты старше 6 часов; рядом указаны её возраст
  и причина. Новые темы появятся после следующего успешного запуска GitHub; очередь автозагрузки при этом работает.
  Обновить сразу можно вручную: GitHub → Actions → Refresh film feed → Run workflow.
- `MirrorRollback` — пришла копия старше уже использованной (обычно кэш CDN на несколько минут), она пропущена.
  `MirrorSourceStale` — документ ленты старше заявленного времени копии, она пропущена.
- `FEED GAP` в `monitor.log` — между двумя использованными копиями мог быть пропуск тем (окно ленты превышено).
- «Недостаточно данных: непрерывная история отдачи N ч из 73 (последний перезапуск: …)» — дождаться 73 часов
  без пропусков опросов больше часа; причина перезапуска указана в скобках.
- F5 обновляет отображение HTML, а не запускает опрос.

Пользователь подтвердил чтение 426 раздач, определение всех путей и работу расписания;
тест `/DIRECTORY` сохранил файл на D: со статусом 100% «Раздаётся».
Получение реальных метаданных проверено в GitHub Actions; infohash и размер повторно проверены в Windows.
Локальные тесты 1.7 охватывают фильтры, исходный список, резерв места, повторный запуск,
сбой запуска, существующий хеш на E:, подтверждение/ошибку пути, опасные имена и повреждённые метаданные.
Полный цикл добавления реального нового фильма на пользовательском ПК предстоит подтвердить после включения.

Автотесты `tests\Run-All.ps1` выполняются в GitHub Actions на Windows PowerShell 5.1 и PowerShell 7 для каждого PR:
анализ спроса, защита истории, гонки и восстановление автозагрузки, расчёт места на D:, проверки копии ленты
(свежесть, откат, разрывы, диагностика), очистка в Dry Run (трёхсуточные симуляции опросов, пропуски, сбросы,
повторные запуски, границы 1 ГиБ, отчёт), разбор `resume.dat` и `.torrent`, а также отсутствие в коде удаления,
перемещения и переименования данных, остановки раздач и изменяющих действий WebUI. Скрипты зеркала проверяются отдельно: `python3 -m unittest discover -s tests -p "test_*.py"`.
Локальный запуск без клиента: `powershell -NoProfile -ExecutionPolicy Bypass -File tests\Run-All.ps1`.
µTorrent, WebUI, GitHub и диск D: заменены заглушками; временные файлы создаются только в `tests\autoload-test-*`
и удаляются. Раннер проверяет, что файлы рядом со скриптами не изменились, поэтому запускайте его не во время опроса.
